# Media matching, binding reconciliation, and delivery lifecycle

Research date: 2026-09-14. Baseline: xRegistry `16483bb564586423de9c128db89f3b61d360f4e3` (documents identify themselves as 1.0-rc4). This supplements the supplied transport research, not its discovery/backend survey.[^baseline]

**Recommendation:** use xRegistry for typed discovery and desired/observed descriptors, a separately implemented controller for admission and durable reconciliation, and a separately deployed connector/data plane for acquisition and delivery. Everything labeled **proposed**, including the algorithms, states, permissions, and acceptance rules below, is this author's original design requirement, not an implemented controller or upstream performance guarantee.

## 1. Verified registry semantics and their consequences

**Capabilities are negotiated, not presumed.** `GET /capabilities` is SHOULD-supported; supported features can vary with the authenticated caller. Filtering is optional: comma-separated expressions in one `?filter` are AND, repeated parameters are OR. Unsupported query parameters SHOULD be ignored, so filters are neither authorization nor proof that every returned offer satisfies the need. Re-evaluate complete candidates locally; inspect pagination support and traverse all available pages.[^cap]

**Concurrency is entity-local.** Supplying the existing non-null `epoch` on an update/delete requires mismatch detection. Creation ignores a supplied epoch; omission/null disables checking. Epochs increase on every update, including empty patches, and need not increase by exactly one. The specified `mismatched_epoch` error is **400**, not an assumed Kubernetes-style 409. A parent's epoch changes for child additions/removals, not edits to existing children. A Resource's `meta.epoch` concerns resource metadata/version membership; its exposed default Version has a different epoch.[^epoch]

For proposed metadata-only binding records, update the fixed Version with its read epoch in the JSON body; when using document resources, HTTP exposes Version metadata through `xRegistry-` headers or `$details`. Never use `ignore=epoch`. Do not use `epoch=0` as create-if-absent, a root epoch as a watch cursor, or metadata touches as desired-revision changes.[^httpwrite]

**ETag is not another spelling of epoch.** The pinned core/HTTP documents define no xRegistry-specific ETag contract or mapping. HTTP itself defines representation ETags, strong comparison for `If-Match`, and `If-None-Match: *` for preventing replacement on creation. Verify the deployed server's selected-representation and conditional-write behavior before relying on it; weak cache validators are insufficient for `If-Match`. Repeated xRegistry PUTs preserve semantic values but still advance epoch/modified time. RFC 5789 requires atomic application of a PATCH document; this does not make several HTTP requests plus camera commands transactional.[^conditions]

**Events are hints to reconcile.** Generation is SHOULD, CloudEvents serialization is optional, and subscription/transport mechanisms are not mandated. Optional `xregcorrelationid` correlates one interaction, not a durable consumer offset. Event data can expose entity epochs, but deletion events exclude them. No ordered, lossless, replayable watch follows from these definitions. Re-read referenced entities, periodically rescan authorized collections, and detect deletions against the previous inventory; a missed capability event must not indefinitely preserve an obsolete plan.[^events]

**References are not reservations.** XIDs may dangle; an existing Version may be replaced. `maxversions: 0` permits pruning non-default Versions at any time, not guaranteed archival retention. The model's `immutable` aspect cannot be applied to extension attributes. Therefore immutable request identities, frozen plans, model digests, historical availability, and reference integrity require controller/storage enforcement.[^versions]

## 2. Proposed profile and matcher

Under `/mediagroups/factory1`, define the following Resource collections. `factory1` is an administrative namespace, not inherently an authorization boundary.

| Collection | Proposed responsibility |
|---|---|
| `actors` | Stable workload/connector identity, authorized principal association, execution placement and supported backends. |
| `sources` | Stable physical/logical source identity, ownership policy, private locator/secret reference, and named `offers` map. |
| `needs` | Workload input contracts, hard constraints, ordered preferences, allowed transformations, synchronization and delivery obligations. |
| `bindings` | Desired revision, selected source/offer snapshots, consumer, transform graph, delivery policy and release intent. |
| `bindingstatuses` | Controller-owned observations, applied/ready revisions, conditions, sessions, fencing identity and errors. |
| `assets` | Still/clip/result manifests, content digests, provenance, coverage, access broker reference and retention state. |
| `models` | Inference model versions/digests and input contracts; distinct from xRegistry's registry-wide `/model` schema. |

Use metadata-only, single-current-Version records for mutable control descriptions, with explicit stable Version addressing and `maxversions: 1`; retain their audit journal separately. Asset/model bytes can reside in protected external storage. A named offer is nested source data, **not** an independently versioned resource: capture its source Version/epoch and canonical offer digest when binding.

Represent each offer as valid **joint modes**, not independently combinable lists: `(pixel/codec format, dimensions/ROI, frame-rate constraints, exposure/trigger mode, audio tracks, transport, timestamp domain)`, together with conditional constraints and host/backend requirements. Separate advertised capabilities, last verified device capabilities, effective configuration, and delivered samples. Record observation time, expiry, connector/backend version, and device incarnation. OpenCV setter success is not device acceptance; readback and negotiated sample inspection are required.[^readback]

**Matching algorithm:**

1. **Normalize and authorize.** Resolve actor, need, model and source references under the caller's tenant. Check existence, digests, freshness and permitted purpose before exposing private topology. Unknown hard requirements are unsatisfied, not optimistic defaults. Distinguish live acquisition, fresh still capture, finite clip playback and retained recordings.
2. **Enumerate feasible modes.** For each authorized offer, evaluate complete tuples against required video shape/type, audio presence/format, live/finite and seek semantics, accessible transport, installed decoder/SDK, placement, clock quality, loss policy and resource budgets. Optional registry filtering only reduces this search space.
3. **Plan transformations explicitly.** Enumerate bounded transform paths from a real source mode to the required input contract: depacketize/remux, decode, pixel conversion, scale, resample, encode. Annotate loss, precision/color changes, audio handling, execution host, memory/copies, compute and bandwidth costs. Raw-to-compressed encoding is not remuxing. Reject unsupported edges and paths lacking required capacity evidence.
4. **Obtain consent.** Owner policy governs device changes; each consumer governs permissible input degradation. Require explicit consent for lossy encoding, resolution/rate reduction, audio removal or remote processing. Place transformations where device access, acceleration and data-residency policy permit; prefer shared compatible processing only when measured cost and isolation justify it. Do not silently retune the camera to make a cheaper plan.
5. **Check shared-source admission.** Compare the proposed capture configuration with all active reservations. Reuse the existing capture mode when compatible; otherwise select an authorized downstream transform, another offer/source, or an explicitly consented coordinated reconfiguration. Reject with a concrete conflict when no solution exists. Preserve the recording obligation even if the inference consumer disappears.
6. **Rank only feasible candidates.** Apply the need's declared preference order, for example no device disruption, no lossy conversion, then measured cost and placement preference. Use deterministic source/offer/digest tie-breaking and a declared switching penalty/hysteresis. No favorable preference score can override a hard audio, freshness or ownership predicate.
7. **Reserve and verify.** Atomically reserve the complete source/compute/storage set in the controller's transaction store, then recheck revisions, permissions and capability freshness. Acquire ownership before mutating configuration. Read back camera/transport settings and inspect actual delivered tracks; disagreement invalidates admission or produces an explicitly accepted degraded alternative, never silent success.

Latency feasibility before acquisition is provisional: classify it as unknown unless applicable measurements exist, and require a bounded qualification period before ready.

**Multi-input needs** use an all-or-none reservation plus explicit input slots and clock/skew requirements. Join by mapped capture timestamps or supported trigger identities; bound waiting and define whether an unmatched input fails the bundle or permits an explicitly marked partial bundle. PTP clock agreement alone is not simultaneous exposure. RTP audio/video timestamps require mapping to a common reference, normally RTCP sender-report pairs with verified clock quality; receipt timestamps alone cannot establish exposure synchronization.[^clocks]

## 3. Proposed controller and ownership protocol

Keep `bindinguid` as a never-reused incarnation identity, `desiredrevision` as a controller-authorized monotonic semantic revision, and `planhash` as a frozen accepted-plan digest. Registry epochs protect descriptor updates; they are **not ownership fences**. The API maintains a durable uniqueness constraint on `(tenant, requestid)`: identical requests return the same binding/revision; reuse with a different normalized body is rejected.

For this proposal, the separate binding API commits desired intent/revisions in the controller store and is the sole writer of their registry projections. Independently registered needs/catalog changes are revalidated on admission. Direct descriptor edits cannot bypass the authoritative revision, ownership and operation checks.

Status records identify `bindinguid`, `observedrevision`, `appliedrevision`, `readyrevision`, controller identity, fence, attempt identity, conditions and timestamps. `observedrevision` means reconciled/evaluated, not successful. Status for revision N can coexist with desired N+1, but cannot imply current readiness. Readiness requires matching current desired revision and plan, an active authorized ownership/session lease, verified required tracks, and satisfied qualification conditions. Registry publication is a projection of this state, not its transaction boundary.

| State | Meaning and permitted progress |
|---|---|
| `requested` | Durable desired intent exists; admission pending. Goes to accepted, failed, or draining on cancellation. |
| `accepted` | Frozen feasible plan and reservations exist; no claim that media is flowing. Goes to applying or draining. |
| `applying` | Fenced capture, transform and delivery setup is underway. Goes to ready, degraded, failed, or draining. |
| `ready` | This revision's qualification succeeded; continuous conditions remain monitored. |
| `degraded` | Explicit unmet condition/gap or provisional recovery; mark unusable if any hard input contract fails. Recover through applying/ready or fail. |
| `failed` | This revision/attempt cannot satisfy its contract; expose reason, retryability and cleanup status. No automatic fresh intent. |
| `draining` | No new work admitted; finalize or abandon in-flight work under declared deadlines, revoke access and release owned resources. |
| `released` | Cleanup verified and reservations removed; terminal for this incarnation. |

An update supersedes the old revision, not necessarily the working data plane immediately. If resources permit, qualify a replacement before switching, label output with its revision, and drain only the old branch. Otherwise obtain disruption consent. A failed new revision must not relabel an old stream as ready. Failed attempts retain cleanup obligations; retry is explicitly scheduled through admission/applying, not an unbounded hidden loop.

**Reconciliation sequence:** authenticate desired state; read authoritative current revision; claim work; reserve; persist accepted plan and an operation journal; apply steps; read back; publish observations; maintain health. A durable outbox publishes registry/status changes after controller transactions, retrying projection failures. Status writers use epoch checks and the controller's current-revision guard; they never overwrite a newer desired record. Rescans repair missing notifications and reconcile orphaned sessions.

**Fencing and duplicate prevention are implementation requirements.** Use a strongly consistent lease/claim authority allocating a monotonically increasing fence per source incarnation. A single acquisition gateway owns the SDK/device handle and is the only permitted actuator. It durably records the highest accepted fence and operation keys `(bindinguid, desiredrevision, stepid)`; retries cannot evade deduplication by obtaining a new fence.

Before each mutation, the gateway validates current authorization/lease, rejects older fences, and serializes journal/check/action processing. A completed operation returns its recorded outcome. A new owner must wait for already-started operations to complete or be definitively aborted; fencing cannot recall a hardware command already issued. Loss of renewal/authority stops new mutations. Lease time uses the authority's clock with bounded local validity, not unsynchronized worker wall clocks.

For example: owner A starts step S under fence F; after A loses ownership, its delayed retry is rejected, even if it knows an old registry epoch. Owner B with F+1 consults S's journal instead of blindly replaying S. Absolute configuration setters may be recovered by readback. Non-idempotent triggers or commands with ambiguous crash outcomes require device-level deduplication or explicit uncertainty/failure, **not automatic retry**. If competing gateways cannot fence each other at the actuator boundary, require proven old-owner quiescence/isolation before takeover; otherwise reject automatic failover. A lease document alone cannot satisfy this safety property.

**Cancellation and cleanup:** persist release intent as a new desired revision, invalidate pending work, stop admissions, close only binding-owned readers/transforms, finalize bounded recording segments, then release reservations. Shared acquisition stays alive until all obligations end. Track every side effect's ownership and compensator; unresolved cleanup stays draining/failed with alarms, not released. Keep a tombstone/journal to reject late operations and perform orphan sweeps. Avoid deleting the desired descriptor as the cancellation signal.

Cleanup uses the same fencing and operation journal as setup. Restore previous camera settings only while still owning the source and after checking intervening configuration and remaining reservations. An obsolete attempt must not reset a new owner's camera, close a replacement session, or revoke its grants.

**Resume:** ordinary live reconnect begins a new stream incarnation and reports its gap; no unrecorded frames can be replayed. Finite processing resumes only against an unchanged asset digest and a persisted checkpoint, with decoder/keyframe preroll and overlap deduplication. Distinguish EOS from timeout, decode failure and cancellation. Replaying retained media is a separate authorized processing intent, not silently continuing live delivery.

## 4. Optional relay and two deployment scenarios

**Verified option: MediaMTX v1.21.0**, pinned at `2c6727904fbf233615de74a6c54a9b94dbf6025d`. One path connects one source/publisher to multiple readers. It can initiate an upstream RTSP read, or accept a connector's published stream. External FFmpeg/GStreamer supplies generic-webcam capture and general re-encoding; do not attribute USB3/GigE acquisition, camera controls, or arbitrary transcoding to MediaMTX. Narrow protocol adaptations exist, so "never converts anything" is also inaccurate.[^relay]

RTSP, HLS and WebRTC are relevant read options, but their track/codec intersections differ. The pinned WebRTC path selects at most one video and one audio track and can omit others; AAC input is not automatically made into supported WebRTC audio. Choose delivery protocols per workload, not a generic "camera URL." Bounded relay queues can discard data; overflow is not the inference policy of dropping the oldest decoded frame.[^relaylimits]

**Proposed delivery contract:** distinguish transport receipt, decoded-frame availability, completed processing, and durable asset/result commitment. A relay reader connection or binding's ready state establishes none of the later acknowledgements. Each fanout branch has its own progress and failure accounting; one successful reader cannot acknowledge another. Retrying notifications and idempotent result commits do not establish end-to-end exactly-once media delivery.

### Scenario A: drop-stale inference plus loss-sensitive clip recording

| Concern | Inference branch | Recording branch | Shared decision |
|---|---|---|---|
| Acquisition | Decode required video; omit audio only for this branch. | Preserve required offered audio/video; reject absent required audio. | Capture/pull once in a jointly feasible source mode. |
| Pressure | Bounded latest-frame queue; discard stale decoded frames before inference. | Durable spool/recorder with declared backlog budget; surface gaps. | Separate branch execution; finite queues alone cannot provide indefinite isolation. |
| Latency/loss | Enforce capture-to-inference age contract, count policy drops. | No intentional loss within its admitted interval; verify sequence/coverage. | Exhausted spool or upstream loss degrades/fails recording; never silently claim completeness. |
| Lifetime | Detach/reconnect without owning camera reconfiguration. | Acquisition remains reserved until interval finalization. | A vanished inference reader must not stop required recording. |

MediaMTX's on-demand source lifecycle follows reader demand; its internal recorder must not be assumed to keep that source alive. Use a controller-managed acquisition reservation/always-active source for recording obligations. Its recorder also uses bounded queues, and incomplete final recording parts can be lost on failure: this is not a lossless archive guarantee.[^record]

### Scenario B: local USB/GigE connector, two remote workloads

| Stage | Local connector/controller | Remote inference | Remote archive/indexing |
|---|---|---|---|
| Device ownership | One authorized UVC/native USB3/GigE acquisition path; retain/copy buffers safely before requeue. | No USB index, SDK handle or camera-control privilege. | No independent attempt to configure the same device. |
| Publication | Encode/transform externally if necessary; publisher pushes to relay ingest. | Reader opens an authorized relay output, then decodes locally. | Independent reader consumes supported tracks, or receives finalized asset notifications. |
| Budget | Admit aggregate uplink, encode, spool and reader costs; do not promise multicast or zero-copy. | Local drop-stale policy and freshness measurements. | Backlog/coverage/checksum accounting independent of inference progress. |
| Failure | Fence stale publishers/gateways; reconcile capture and relay path separately. | Reconnect reports a live gap. | Recover only retained intervals; deduplicate completed asset processing. |

For relay-pulls-source, by contrast, configure an accessible RTSP upstream: readers connect to the relay, which initiates the camera session. This is not remote native USB access. Set `overridePublisher: false` where replacement must be rejected, but that protects only one relay path, not physical-camera ownership.[^relayownership] The earlier Aravis buffer-lifetime caveat remains relevant: copying after native memory has already been requeued is too late.[^buffers]

## 5. Proposed access, callbacks, artifacts, and retention

**Separate descriptor visibility from resource authorization.** xRegistry leaves authentication/authorization implementation-specific; endpoint authorization metadata describes how authorization is obtained and explicitly forbids credential configuration.[^auth] Grant distinct permissions for catalog discovery, need submission, source control, binding revision/release, controller status writes, relay publish/read, playback, asset retrieval/deletion, and model access. Reject actor/principal spoofing. Group membership and filter predicates are not ACLs.

Use opaque tenant-scoped secret references resolvable only by the assigned connector/broker; never put secrets into descriptors, examples, events or logs. Redact camera IPs, serials, physical location and network topology from shared catalogs, errors, metrics labels and exports. Enforce tenant boundaries on direct XID reads, linked resources, list counts, callbacks and download endpoints, not just portal screens. Shared physical sources need explicit owner-approved cross-tenant sharing.

After resource authorization, an access broker may return a short-lived, audience/action/path-scoped delivery grant. Prefer authorization headers; where a client requires a signed URL, keep it outside durable registry data and redact it from histories/logs. Bound expiry by the binding lease and asset lifetime; distinguish stable locator, token lifetime and live-session lifetime. Expired/revoked access must stop new requests and terminate or reauthorize existing sessions by policy; handshake authentication alone is insufficient. RFC 6750 supports scoped short-lived tokens, transport protection and avoiding tokens in page URLs.[^bearer] MediaMTX offers publish/read/playback path permissions, but its API permission is not equivalently path-scoped; isolate its administration behind a tenant-aware service.[^relayauth]

**Callbacks:** register and authorize destinations; restrict allowed hosts/egress and redirects. Commit notifications to a durable outbox with stable event identity, binding revision, result reference and attempt history. Retry with bounded backoff; acknowledge receipt separately from processing; retain dead-letter failures. Receivers durably deduplicate notifications. If using HTTP Message Signatures, define covered method/target/body digest plus created/expiry/nonce checks; signatures alone do not stop replay.[^callbacks] MediaMTX segment hooks launch external commands, not a verified durable callback/acknowledgement queue.[^hooks]

**Assets/results:** publish a manifest only after finalization and digest verification, with required tracks, capture interval, source/stream incarnations, frame/gap coverage, model/transform digests and retention policy. Distinguish complete, partial, corrupt and expired. A fresh URL does not make an old snapshot/result fresh. Keep authoritative expiry checks at the resource server; maintain an independently auditable purge deadline for storage, replicas and indexes. Cancel readers before removing in-use temporary data; account for authorized retention holds explicitly. Descriptor deletion is not byte deletion.

Stage content-addressed bytes before atomically committing the result manifest, index reference and notification outbox record. Sweep abandoned staged objects. Downstream consumers need their own durable uniqueness/transaction boundary; arbitrary external side effects are not made exactly-once by a registry attribute.

MediaMTX supports recording and HTTP playback, but the pinned playback implementation rejects MPEG-TS recordings; use verified fMP4 playback where needed. Periodic recording cleanup is not exact-deadline revocation. Protect required assets independently of registry version pruning, and do not promise missed-live catch-up merely because playback exists.[^playback]

## 6. Measurable acceptance criteria, without invented targets

Operators/needs supply the limits below before admission. Missing limits or unavailable measurements cannot establish a hard guarantee. Test on the intended hardware, backend, codec, load and failure conditions; no numerical latency/throughput promise is inferred here.

The proposed need names its `maxframeagems`, `maxavskewms`, `maxinputskewms`, `readydeadline`, backlog limits, freshness limits and expiry/purge deadlines, plus the measurement window and quantile where applicable. Do not substitute an implementation default for an omitted hard contract.

| Metric | Definition and proposed pass condition |
|---|---|
| Frame age | At inference start, mapped processing time minus capture time. Include clock-mapping uncertainty in the upper bound; require the declared worst-case or percentile budget. Reject over-age frames. If only receive time exists, label the metric receive-age, not capture-age. RTP jitterbuffer `latency` is not this metric.[^clocks][^queues] |
| A/V and input skew | A/V: absolute difference between corresponding mapped presentation timestamps. Multi-input capture: difference between mapped capture timestamps. Use the declared common clock and uncertainty; require the respective skew limit and clock-quality bound. Do not mix receipt, capture and presentation times or compare raw audio/video RTP timestamps. |
| Drops and completeness | Per stream incarnation, separately count acquisition gaps, corruption, queue drops, policy skips, relay packet discards and consumer rejection. Do not add packet counters as frame counters. Verify recording against known sequence/coverage boundaries; unknown upstream loss cannot become "zero loss." |
| Ready latency | Qualification time minus durable request-commit time, on a declared common clock; use monotonic elapsed time within a process, and account for clock uncertainty across restart/failover. Separately report admission/apply/first-sample durations and deadline failures. A prior revision's ready time cannot satisfy a new revision. |
| Ownership/idempotency | Fault-inject lost replies, renewal failure, takeover and late retries: no stale-fence mutation starts; each operation key has one definitive effect or an explicit uncertain outcome, never blind repetition. |
| Expiry/freshness | Reject access after the declared expiry-enforcement deadline, verify purge completion against its separate deadline, and compare snapshot/result capture age with the need's freshness limit. |
| Result dedupe | Enforce one committed result per tenant, processing-intent ID, input digest/window or source-incarnation/frame IDs, and model/transform digest. Duplicate deliveries produce no duplicate index/archive side effects; deliberate reprocessing gets a new intent ID. |

Also stall each fanout branch independently, drop/reorder registry events, cancel during every applying step, and restart after journal writes. Accept only if isolation, convergence and cleanup meet the explicitly declared budgets; otherwise reject admission or report the precise degraded condition.

## 7. Unresolved normative boundaries

The media profile, controller transactions/fences, replay contract and access/retention enforcement remain to be specified and implemented. `/endpoints/<id>` is an xRegistry **Group**, not a versioned media Resource; additional protocol names are permitted, but RTSP/native-camera option contracts are not thereby standardized. Endpoint usage is client-relative and cannot combine producer with other usages.[^endpoint]

Do not invent nested controller action URLs beneath registry entities: the HTTP binding prohibits non-root extension APIs.[^extensionapi]

One concrete pinned-document inconsistency remains: HTTP's `/capabilities` example uses an `available` array and separate `mutable` list, whereas core defines `available` as a map containing per-entry `mutable`. Implement against the normative core shape, not that sample, and verify interoperability with the chosen server.[^capexample] None of these findings requires a repository edit or establishes runtime delivery guarantees.
